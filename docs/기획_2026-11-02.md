# project-corebank: 미니 코어뱅킹 플랫폼

작성일: 2026-11-02 / 상태: 방향 확정, 상세 설계 전

## 1. 추천 방향

**미니 코어뱅킹 플랫폼**을 첫 주제로 제안한다. 계좌 개설, 입출금, 계좌 이체, 거래내역 조회, 일 마감 대사를 처리하는 서버다.

- 금융권 개발의 핵심인 원장, 트랜잭션, 동시성, 중복 처리 방지, 대사를 한 프로젝트에서 모두 다룬다.
- 실제 돈과 외부 기관 연동 없이 혼자 만들 수 있고, 기능을 단계별로 늘리기 쉽다.
- 카드 결제나 대출처럼 다른 금융 업무로 확장할 수 있는 기반이 된다.

목적은 은행, 카드사, 증권사 지원용 포트폴리오다. 1차로 코어뱅킹을 완성하고, 시간이 남으면 같은 원장 위에 카드 승인·정산을 2차로 붙인다.

## 2. 후보 비교

평가는 1인 사이드프로젝트를 기준으로 한 주관적 판단이다.

| 순위 | 후보 | 핵심 기능 | 익히는 기술 | 난이도 | 주의할 점 |
|---|---|---|---|---|---|
| 1 | 미니 코어뱅킹 | 계좌, 이체, 원장, 일 마감 | 트랜잭션, 락, 멱등성, Spring Batch | 중 | 서버 중심이라 결과를 테스트와 문서로 보여줘야 한다. |
| 2 | 결제 승인·정산 | 승인, 취소, 가맹점 정산 | 상태 머신, Kafka, 대사 | 중상 | 외부 기관을 모의 서버로 만들어야 한다. |
| 3 | 이상거래 탐지(FDS) | 룰 기반 탐지, 알림, 심사 화면 | 스트리밍, 룰 엔진, 머신러닝 | 중상 | 거래 데이터를 직접 생성해야 한다. |
| 4 | 대출 심사 | 신청, 심사, 실행, 상환 스케줄 | 워크플로, 금융 계산, 배치 | 중 | 업무 지식이 많이 필요하다. |
| 5 | 증권 주문 매칭 | 호가창, 주문 체결, 시세 전파 | 저지연 처리, WebSocket | 상 | 성능 중심이라 일반 금융 업무와 거리가 있다. |
| 6 | 블록체인 원장 | 토큰 발행, 이체, 합의 | Fabric 또는 Besu, Solidity | 상 | 금융권 활용 범위가 아직 좁다. |

## 3. 1차 범위

**만드는 것**

| 기능 | 내용 | 핵심 포인트 |
|---|---|---|
| 계좌 | 개설, 조회, 해지 | 계좌 상태 관리 |
| 입출금 | 입금, 출금 | 잔액 부족 거부 |
| 이체 | 내부 계좌 간 이체 | 출금과 입금을 하나의 트랜잭션으로 처리 |
| 원장 | 복식부기 분개 기록 | 수정하지 않고 추가만 하며, 정정은 역분개로 처리 |
| 중복 방지 | 요청별 멱등성 키 | 같은 요청을 재전송해도 한 번만 처리 |
| 거래내역 | 계좌별 기간 조회 | 페이지네이션 |
| 일 마감 | 잔액과 원장 대사 배치 | 불일치 발견 및 기록 |
| 감사 로그 | 누가, 언제, 무엇을 했는지 기록 | 변경 이력 추적 |
| 고객 화면 | 로그인, 계좌 조회, 이체, 거래내역 | 이체 실패와 중복 클릭 처리 |
| 관리자 화면 | 계좌 및 거래 조회, 일 마감 결과, 감사 로그 | 대사 불일치 확인 |

**만들지 않는 것**: 실제 은행 연동, 실제 개인정보 처리, 모바일 앱, 대출, 마이크로서비스 분리.

**기술 스택**

| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 | Java 25(LTS), Spring Boot 4.1.2, Spring Batch | 안정적인 최신 LTS 사용. 금융권의 구버전 환경과 다른 점은 README에 정리 |
| 빌드 | Gradle | 사용자 선택 |
| DB | Oracle Database Free | 은행, 카드사, 증권사 코어 시스템에서 많이 쓰는 계열 |
| 데이터 접근 | Spring Data JPA, 대사와 집계는 네이티브 SQL | 사용자 선호. 실행 SQL을 로그로 확인하고 핵심 SQL은 직접 작성 |
| 마이그레이션 | Flyway | 스키마 변경 이력 관리 |
| 프론트엔드 | React, TypeScript, Vite | 구현과 설명은 Claude가 담당 |
| 테스트와 실행 | JUnit, Testcontainers, Docker Compose | 실제 DB로 동시성 테스트, 간편한 실행 |

**역할 분담**: 원장과 이체 같은 백엔드 핵심은 직접 작성하고 Claude가 설명과 리뷰를 맡는다. 화면은 Claude가 작성하고 구조를 설명한다.

## 4. 접근 방식

기능보다 "돈이 틀어지지 않는다"는 것을 먼저 증명하는 순서로 진행한다. 작업일은 하루 6시간 기준의 대략적인 추정이며, 합계는 약 32일이다.

| 단계 | 할 일 | 완료 기준 | 작업일(추정) |
|---|---|---|---|
| 0. 업무 이해 | 용어 정리, 이체와 원장 흐름 정리 | 계좌 이체 한 건의 분개를 설명할 수 있다. | 2 |
| 1. 설계 | ERD, API, 불변 조건, 상태 정의 | 설계 문서를 Git에 커밋했다. | 3 |
| 2. 프로젝트 기반 | Git, Spring Boot, DB, 마이그레이션, CI | 빈 API와 DB 연동 테스트가 CI에서 통과한다. | 2 |
| 3. 핵심 원장 | 계좌, 입출금, 이체, 원장 | 모든 거래의 차변과 대변 합이 일치한다. | 7 |
| 4. 안정성 | 동시성 제어, 멱등성, 에러 처리 | 동시 이체와 재전송 테스트에서 잔액이 맞다. | 5 |
| 5. 마감 | 일 마감 배치, 대사, 감사 로그 | 일부러 만든 불일치를 배치가 찾아낸다. | 4 |
| 6. 화면 | 고객 화면, 관리자 화면 | 화면에서 이체부터 대사 결과 확인까지 시연할 수 있다. | 6 |
| 7. 공개 | README, 아키텍처 그림, 설계 결정 기록, 부하 테스트 | 처음 보는 사람이 Docker Compose로 실행할 수 있다. | 3 |

### 처음부터 지킬 불변 조건

1. 모든 거래의 차변 합과 대변 합은 같다.
2. 계좌 잔액은 해당 계좌의 원장 합계와 같다.
3. 출금 가능 계좌의 잔액은 음수가 되지 않는다.
4. 같은 멱등성 키의 요청은 한 번만 반영된다.
5. 원장 기록은 수정하거나 삭제하지 않는다.

금액은 `double`을 쓰지 않고 원화 기준 정수 또는 `BigDecimal`을 쓴다. 이체할 때는 계좌를 항상 같은 순서로 잠가 데드락을 줄인다.
